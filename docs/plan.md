## 設計のポイント

- 音声は端末から出さない。保存するのは特徴量7つ（n, dur, gap, f0, cent, gapCv, durCv）と正解ラベル、判定、時刻だけ。
- 判定 = ルール（Pongrácz 2005 を単純化）と、飼い主が教えたサンプルの kNN（k=5、距離重み）を、サンプル数 n に応じて n/(n+8) でブレンド。試作と同じ。
- iPhone はバックグラウンド録音ができないので、画面が隠れたら監視を止めて通知する。Wake Lock で監視中は画面を消さない。
- 「本物の翻訳ではなく推測」を判定欄・注意書きの2か所に常時表示。
- 屋号は UI に出していない。

## plan #14 の設計メモ（2026-11-05。YAMNet を本体 mic.js の前段に入れる）

計測（`docs/accuracy.md` 2026-11-03〜05）から決めたこと。実装はこのメモどおりに小さく進める。

1. **渡す単位と範囲**: mic.js が確定した「吠えの塊」そのもの（約 1 秒）ではなく、リングバッファ（過去 6 秒）から**前を足して最低 MIN_SEC 秒の実音**を渡す。未来の音は待たない（判定の遅れを増やさない）。**MIN_SEC = 2**（2026-11-05 の計測: 2 秒で犬 94%・犬以外 0%、3 秒は犬以外を 1 塊拾う。`docs/accuracy.md`）。`Listener` に `contextSec` を足し、`onCluster(x, sr, { wide })` の第 3 引数で文脈つき波形を渡す。特徴量（気持ちの判定）は従来どおり塊そのもの `x` から取る。
2. **しきい値**: 犬らしさ（犬系 7 クラスの最大値）**0.3**。犬系の合計 dogSum は使わない。
3. **3 つの状態**: (a) **未準備／オフ／オフライン** → 従来どおり音量だけで動く（いまと同じ）。(b) **犬（0.3 以上）** → 従来どおり判定して履歴に残す。(c) **犬以外っぽい（0.3 未満）** → **捨てない**。判定はするが薄く表示し（「犬の声ではないかも」の注記）、育成ログには自動では残さない。飼い主が正解をタップしたら、その時点で「犬」と確定して通常どおり保存する（くんくん・息が落ちても「さみしい」を教えられる）。履歴の件数・吠え回数の表示は (b) だけを数える。
4. **読み込み**: tfjs 4.22.0（jsdelivr 固定版）とモデル（TF Hub v1、約 15MB）は**監視を開始してから裏で**読む（`<script>` を動的に足す。初回のみ、2 回目はブラウザキャッシュ）。読めるまで・失敗したら (a)。service worker の事前キャッシュには入れない（本体のオフライン起動を重くしない）。
5. **既定はオフ**: `app/js/dogcheck.js`（仮）として入れ、設定（localStorage `wl.dogcheck`）で明示的に「オン」にしたときだけ読む。E2E は既定オフのまま通す（ネットに出ない）。スマホの処理時間（塊 1 つ CPU 0.3〜0.5 秒＝Actions のランナー。実機は未計測）と電池への影響を実機で見てから既定オンを検討する。
6. **順番**: ①`Listener.contextSec` と第 3 引数（単体テスト）**＝完了 2026-11-05** → ②`dogcheck.js` の読み込み・判定（実験室 `app/lab/yamnet.js` の純粋関数をそのまま import）**＝完了 2026-11-06** → ③状態 (c) の表示と「教えたら保存」**＝完了 2026-11-07** → ④設定トグル**＝完了 2026-11-08**。1 晩 1 つずつ。
7. **② で分かったこと（③・④ で反映する）**: (i) 推論は 2 秒の音に約 0.9 秒（Actions のランナー）かかるので、**判定は待たせずに先に出し、犬らしさは後から届く**。③ の「薄く表示」は後から薄くする形になる（先に通常表示 → 0.3 未満と分かったら薄くして注記）。(ii) いまの `sw.js` は外部オリジンの GET を全部「ネットワーク優先＋キャッシュに保存」するので、オンにすると tfjs とモデル（約 15MB）も Service Worker のキャッシュに入り、VERSION を上げるたびに消える。既定オンにする前に、jsdelivr / tfhub / kaggle は SW のキャッシュに入れない（ブラウザの HTTP キャッシュに任せる）ように直す。**→ 2026-11-07 に対応済み**（`sw.js` wl-v9: 外部オリジンでキャッシュするのは fonts.googleapis.com / fonts.gstatic.com だけ。それ以外は respondWith しない）。(iii) tfjs の `<script>` に SRI（integrity）を付ける（npm の tarball からハッシュを出し、Actions で実際に読めることを確かめてから）。**→ 2026-11-08 に対応済み**（`TFJS_SRI`。E2E の偽 tf は、同じページの `lab/yamnet.js` の `TFJS_SRI` も偽のハッシュに差し替えて通す。Service Worker が効いている E2E では差し替えられないので「偽 tf は SRI で拒まれて failed になる」ことを確かめる形にした）。(iv) 録音ファイル読み込みにはまだ犬の声チェックを掛けていない（マイク監視だけ）。

8. **③ で決めたこと（2026-11-07）**: (i) 状態 (c) は「まだ答えを待っている判定」にだけ掛ける。犬らしさが届く前に飼い主が教えた・「わからない」を押した場合は何もしない（数字を添えるだけ）。(ii) 育成ログへの保存はもともと「飼い主が教えたときだけ」なので、(c) で追加で止めるものは無い。変えたのは表示（薄くする・注記）と「吠え ◯回」の数え方だけ。(iii) 前の推論がまだ終わっていない・推論に失敗した塊は状態 (a) 扱い（従来どおり数える）。(iv) 録音ファイル読み込みにはまだ掛けていない（7-iv のまま）。

9. **7-iv の検討（2026-11-09）: 録音ファイル読み込みには当面掛けない**。理由: (i) 犬の声チェックの値打ちは「マイク監視中に人の声・物音を吠えと取り違えない」ことにある。録音ファイルは飼い主が自分で選んだ「犬の声のつもり」の音なので、犬以外が混ざる場面がそもそも少ない。(ii) くんくん・息は YAMNet が落としやすい（`docs/accuracy.md` 2026-11-05）ので、飼い主が選んだ録音を「犬の声ではないかも」と薄くすると、助けになるより気分を害する方が多そう。(iii) モデル（約 15MB）はいま監視開始後にしか読まないので、ファイル用には読み込みの入口（ファイルを選んだとき）を増やす必要があり、既定オフのまま入口だけ増える。やるなら小さい: `runFile` でデコード済みの音をそのまま（長ければ最初の塊の終わりまでの 2 秒を `clustersFromEvents(minSec: 2)` と同じ範囲で）`runDogCheck` に渡し、`startDogCheck()` をファイル選択時にも呼ぶ、で 30 行ほど＋E2E 1 本。**社長から「録音ファイルでも人の声を拾って困る」という声が出たら、そのとき入れる**。

## plan #13b の設計メモ（2026-11-14。「声の大小のばらつき」を特徴量に足す案。机上、数字は変えない）

`docs/accuracy.md` 2026-11-13 の表で、くんくんは「同じファイルのいちばん大きい声から中央値 5.4 dB 下」、吠えは 0.7〜1.6 dB だった。これを本体の特徴量にする案。実装は正解ラベル付きの本物の犬が来てから（#13 の MFCC と一緒に効果を測る）。

1. **足す数字は 1 つ、`lvlDrop`（dB）**: 塊の中の声 1 回ごとの `level`（`events[].level`、検出器が見た RMS のピーク。すでに出している）を、**塊の中でいちばん大きい声からの dB 差**（`20·log10(level / max)`、0 以上）にして、その**中央値**。吠えの連吠え ≒ 0〜2、くんくん ≒ 5。`levelCv`（変動係数）でなく dB 差にする理由: 録音ごと・端末ごとの音量の基準に左右されない（accuracy.md の 5 本は -22〜-24 dBFS に正規化されていた）、「なぜ」に「小さい声が混ざる（いちばん大きい声から 5dB 下）」と言葉で出せる、accuracy.md の表と同じ数字で突き合わせられる。
2. **1 回しか鳴いていない塊（n=1）は測れない**: `lvlDrop = 0` で保存し、`terms()` では f0=0 のときと同じ流儀で「どちらとも言えない 0.5」にする（`n >= 2` のときだけ使う。`explain()` の `termUsable` にも同じ条件）。
3. **古いデータとの互換**: `store.js` の保存形式（`samples[].f`）はキーが増えるだけ。`lvlDrop` が無い古いサンプルは `f.lvlDrop ?? 0` で読み、`vec()` では 0（＝吠えと同じ側）に置く。`importJSON` の検査（`typeof s.f.n === 'number'`）はそのまま通る。保存形式のバージョン（`wanlingual.samples.v1`）は上げない（増えるだけで壊れない）。
4. **kNN の正規化**: `vec()` に `clamp(f.lvlDrop, 0, 12) / 12` を 1 本足す（7 → 8 次元）。12 dB は息（パンティング）の 12.8 dB が上限になる値。既存の 7 本は触らないので、古いサンプル同士の距離は √(7/8) 倍ほど縮むだけで順位は変わらない。
5. **ルールの項**: `terms()` に `uneven = clamp((lvlDrop - 1.5) / 4, 0, 1)`（1.5 dB で 0、5.5 dB で 1）と `even = 1 - uneven` を足す候補。使い方は accuracy.md 2026-11-13 の方向どおり、**さみしい** に `uneven`（「長い 0.5」を減らして入れる）、**威嚇** に `lowP` と並べて `uneven`。ただし遊びのうなりも 4.6 dB だったので、さみしい と 威嚇 の区別は `lowP`（うなり 358Hz vs くんくん 459Hz）に任せる。**重みの数字は正解ラベルが来てから**。
6. **方針の確認**: `level` は音量 1 つの数字で、音声そのものではないので「音声データは端末から出さない」に影響なし。マイクは `autoGainControl: false` で開いている（`mic.js`）が、iPhone は無視されることがあるので、実機で連吠えの `lvlDrop` が 0〜2 dB に収まるかを見てから（AGC が効くと差が潰れて くんくん も 0 に寄る）。
7. **1 回の中のピッチの傾き `f0Slope`（見積もりだけ）**: `features.js` の `picks` は 1 回の声の中を最大 6 点見ているので、各点の f0 を時刻つきで持ち（`picks` を時刻順に並べ直す。いまは `pf` を最後に push しているので順不同）、**最初と最後の f0 の差を半音（cent）に直したもの**を `events[].f0Slope` に、塊では中央値を `feats.f0Slope` に出す。変更は `features.js` に 6〜8 行、`vec()`・`terms()` に各 1 行、単体テスト 1〜2 本（上がる合成音・下がる合成音）。ただし accuracy.md 2026-11-13 ではくんくんの f0 の幅は特別広くなかったので、**先に `lvlDrop` だけ入れて効果を見る**。順番: (i) `lvlDrop` を `feats` に出す＋表示（判定には使わない）→ (ii) `vec()` に足す → (iii) `terms()`・重み（正解ラベルが来てから）。1 晩 1 つ。

## plan #13 の下調べ（2026-11-14。MFCC をライブラリ無しで自前で出す手順と計算量）

実装はしていない。`tools/mfcc-bench.mjs`（純粋関数＋計測。`node tools/mfcc-bench.mjs` で表が出る。単体テスト `tests/unit/mfcc-bench.test.mjs` 5 本）で手順と速さだけ確かめた。

- **手順**（教科書どおり、`features.js` と同じ frame 1024 / hop 256、FFT は `features.js` の `fft()` をそのまま使う）: ハン窓 → FFT → パワースペクトル 513 本 → **メルフィルタバンク 26 本**（三角、0〜sr/2、m = 2595·log10(1 + f/700)）→ log（床 1e-10）→ **DCT-II（直交）で 13 係数** c0〜c12。塊 1 つの要約は各係数のフレーム平均（＋標準偏差）。c0 は音量に近いので、判定に使うなら外すか別扱い。依存は増えない（約 80 行）。
- **計算量（1 秒の音 ≒ 169 フレーム）**: Node 22 と Chromium で **約 7.5 ms／秒**（Actions のランナー相当の Xeon 2.3GHz、1 コア）。Chromium の CPU スロットリングで 4 倍遅く（中くらいのスマホのつもり）して **30 ms／秒**、6 倍で 49 ms／秒。比較: いまの `analyzeSamples()` は、声の回数で変わる（fixtures の `bark4.wav`＝2.8 秒に 4 回で 3.5 ms／秒、1.5 秒に 4〜5 回鳴く合成の連吠えで 21.5 ms／秒、4 倍遅くして 90 ms）。重いのはピッチの自己相関（1 回の声につき最大 6 か所 × ラグ 460 本 × 2048 点）で、MFCC は声の回数に関係なく一定。**MFCC を足しても判定 1 回（塊 1.5 秒）に 10〜50 ms 増えるだけ**で、「検出から判定まで約 1 秒」は変わらない。
- **保存する数字**: 平均だけなら 13（c0 を外して 12）、標準偏差も入れると 26 増える。`samples[].f` に `mfcc: [..]` の配列で持つ形（kNN の `vec()` では各係数を ±20 くらいで clamp して正規化、ルールには使わない）。音声そのものではないので「音声データは端末から出さない」に影響なし。localStorage の上限（`MAX = 2000` 件）でも 1 件 300 バイト増 → 600KB 程度で問題なし。
- **本物の犬で先に見ること**: ESC-50 dog 40 本と CC0 5 本で、くんくん／うなり／吠えの MFCC（c1〜c12 の平均）が分かれるかを `lab-yamnet` の `features-check.mjs` に表で足す（`report.mjs` に純粋関数、Actions で実行）。これが次の 1 晩ぶん。分かれなければ本体には入れない。
- **入れる順番の案**: (i) `features.js` に `mfcc(x, sr)` を足し `feats.mfcc` に出すだけ（判定・保存は変えない。単体テスト）→ (ii) 保存（`store.js` 互換は #13b と同じ: 無ければ無視）→ (iii) `vec()` に足して kNN だけに効かせる（ルールは触らない）→ (iv) 正解ラベル付きデータで効果を測って `docs/accuracy.md` に書く。
